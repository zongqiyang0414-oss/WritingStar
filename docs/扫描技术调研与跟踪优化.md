# 扫描技术调研与跟踪优化 · v0.13.0 · 2026-10-30

用户明确最慢的是“纸张已入镜，但迟迟不自动拍摄”。本轮针对快门前的识别／框线／稳定计时处理，未声称已完成真实手机耗时或此前两张用户实拍图验证。

## 当前原因与实际修复

1. 过去每帧重复全图多阈值、轮廓和直线搜索。现在首次全图定位后，每帧重新验证四条边的真实亮度过渡，跟踪失败立即丢弃旧框，必要时重新全图定位。空场景全图搜索间隔至少400毫秒，避免持续占满主线程。
2. 过去框线PNG导出与检测累计超过650毫秒，会在稳定条件满足后重新清零。现在稳定条件满足就先触发拍摄，再处理下一次框线显示。稳定时间仍为1.2秒、至少5个可靠观察；后台／陈旧帧、移动与同页锁规则保留。
3. 过去拍照后独立检测，可能改选另一张纸或另一个矩形。现在同一H5视频视野、近期有效识别时，使用最近几帧中位数四角直接裁剪；相机比例变化时重新检测。微信预览和高清照片视野可能不同，保留独立检测，对显著不一致结果进入调角确认。
4. 相册继续逐张独立检测，多选、页序、二维码和60页收件箱规则保留。

## 可复核的本地测量

执行环境为Node v24.19.0；同一420×500合成图，检测分析最长边384，每项预热2次、测量7次取中位数。比较的是已发现纸张后的处理阶段：新跟踪有有效前一帧；旧版和jscanify每次全图重找。没有把它写成整个扫码流程或手机速度倍数。

| 合成场景 | 旧版每帧全图检测 ms | 新版已定位后跟踪 ms | OpenCV＋jscanify默认全图检测 ms |
| --- | ---: | ---: | ---: |
| plain | 82.89 | 3.22 | 10.63 |
| lowContrast | 66.6 | 1.78 | 6.64 |
| shadow | 46.64 | 1.5 | 6.48 |
| printedFrame | 28.45 | 无纸张，不跟踪 | 6.63 |

低对比场景的jscanify默认结果是一条印刷横线（高度约图像的1%），并非正确纸张；新跟踪与原检测均接近已知四角。不能仅凭候选库耗时更低就宣称其效果更好。printedFrame两种全图方法均未输出可用纸张，未声称其中一个误裁。

数据：[比较结果](../outputs/scan-tracking-comparison-20261030.json)。复现脚本：[evaluate-scan-tracking.mts](../scripts/evaluate-scan-tracking.mts)。脚本需要通过SCAN_STUDY_BASELINE_DIRECTORY指定从Git提交11072a1提取的documentScan.js、scanGeometry.js，并用SCAN_STUDY_OPENCV_MODULE和SCAN_STUDY_JSCANIFY_MODULE指定评估用本地模块；用node --import tsx执行。评估模块不在应用依赖中。
